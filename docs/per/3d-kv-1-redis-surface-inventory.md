## Boundary

This is an inventory pass only. It does not choose a backend, implement a Redis-compatible service, or move v0 product logic into `local-sandbox`.

`local-sandbox` should own the local service semantics needed to boot v0: lifecycle, endpoint/profile facts, readiness, diagnostics, command compatibility, expiry behavior, and atomic service operations. v0 should continue to own key names, schemas, product retention policy, rate-limit policy, auth/session semantics, bot/integration payload shapes, and all migrations or cleanup rules that interpret product data.

## Summary

The prepare split is confirmed with one important refinement. Active v0 uses `@upstash/redis` clients in `chat/lib/kv.ts`, an `@vercel/kv` proxy in `web/data/kv/index.ts`, and a separate marketing `@upstash/redis` client in `apps/marketing/lib/kv.ts`. The current active checkout does not contain `PgLocalKV` and does not directly call `eval`, `evalsha`, `scriptLoad`, `multi`, `rpush`, or `ltrim` in the inspected active scopes.

The live active command surface is broader than basic get/set/del. It includes strings, hashes, sets, sorted sets, lists, counters, existence checks, scans, TTL/expiry, pipelines, explicit `setex`, and `set(..., { nx: true, ex/px })` lock-style calls. Web also uses commands not present in the prepare sketch: `expireat`, `exat`, and `zremrangebyrank` through `@vercel/kv` pipelines.

Local boot-critical active usage clusters around VM pool/state, VM gateway locking, anonymous limits, chat and web rate-limit readiness, frame token/session transfer ephemeral data, credential/network-policy helpers, screenshots, OAuth state, integration Redis browsing, and bot auth/database helpers. Many product data paths are not boot-critical for the first readiness gate but still define the service surface a complete local mode will encounter during normal development.

`PgLocalKV` exists in `v0-lima-rfc`, not in active v0. In that branch, `chat/lib/kv.ts` swaps all chat Redis clients to one `PgLocalKV` instance when `VM_PROVIDER === 'vfkit'`, and `dev:local` starts `pglite-server --db chat/.pglite --port 5433 --run pnpm dev:chat` with `PG_LOCAL_URL`. That branch also adds an in-memory local rate-limit adapter for local VM mode, reducing reliance on `@upstash/ratelimit` scripts in local dev. It does not make `web/data/kv/index.ts` local.

## Active-Main vs Lima-RFC Differences

- Active v0 has no `PgLocalKV`; lima-rfc has `chat/lib/pg-local-kv.ts`, `chat/lib/pg-local-kv.test.ts`, and local client selection in `chat/lib/kv.ts`.
- Active v0 has no active-main `rpush` or `ltrim` hits in `chat`, `web`, or `apps/marketing`; lima-rfc has `ephemeralKv.rpush` and `ephemeralKv.ltrim` in `chat/app/chat/api/vm/perf-trace.ts`.
- Active v0 has no direct `eval`, `evalsha`, `scriptLoad`, or `multi` hits in inspected application code; lock behavior is library-mediated by `@upstash/lock` through `chat/lib/lock.ts` and `chat/app/chat/api/vm/gateway.ts`.
- Lima-rfc `PgLocalKV` implements a small `eval` emulation for `@upstash/lock` release/extend scripts but intentionally throws on arbitrary scripts, `evalsha`, `scriptLoad`, and `multi`.
- Lima-rfc local rate limits use `chat/app/lib/rate-limit/local-rate-limit.ts` when `env.usesLocalVMProvider`; active v0 constructs many `@upstash/ratelimit` instances directly.

## Product-Owned Key and Schema Notes

These are product details to keep in v0. They should shape tests and fixtures, but not become `local-sandbox` domain concepts.

- VM product keys: `vm-s-*`, `vm-pool:sandboxes:*`, `vm-pool:metadata:*`, `vm-pool:claim:*`, snapshot keys, and golden snapshot metadata. The daemon may need generic service operations that can store and scan these, but v0 owns their naming and cleanup policy.
- Auth/session keys: `session_transfer:*`, frame-token lookup keys, `oauth-state:v1:*`, Slack/MCP token keys, bot auth keys, and bot DB prefixes. v0 owns encryption, TTL duration, and validation.
- Rate-limit keys: Upstash rate-limit prefixes, anonymous limit keys, web `limit:*` keys, waitlist limits, and daily model usage counters. v0 owns limits, windows, and grace periods.
- Product data keys: users, branches, commits, results, themes, collections, evals, global recent history, screenshots, prompt leak detection, and usage codes. v0 owns all schemas and retention rules.
- Integration browsing route: the Redis integration route creates a Redis client from a user's integration env vars and can inspect `type`, `ttl`, `scan`, strings, hashes, lists, sets, and sorted sets. That is product functionality over external resources, not a daemon-local bootstrap requirement.

## PgLocalKV Coverage Summary

Covered in lima-rfc: `get`, `mget`, `set`, `setex`, `del`, `hgetall`, `hmget`, `hset`, `hmset`, `hdel`, `exists`, `expire`, `sadd`, `srem`, `smembers`, `lpush`, `llen`, `lrange`, `lrem`, `rpop`, `incr`, `scan`, `zscore`, `zadd`, `zincrby`, limited `eval`, and a small pipeline subset.

Missing or materially incomplete against active live surface: `ttl`, `type`, `hget`, `sismember`, `zrange`, `zcard`, `zrem`, `zremrangebyrank`, `expireat`, `exat`, pipeline support for many commands, exact Redis list pop atomicity, exact sorted-set ordering/range semantics, and full Upstash/Redis response parity. Lima-rfc-only `rpush` and `ltrim` are also missing. Active app code did not show direct arbitrary Lua/script/transaction usage, but lock-script compatibility still needs explicit testing because `@upstash/lock` uses scripts through its wrapper.

The current PgLocalKV is valuable evidence, but it is not a drop-in service contract. The riskiest gaps are atomic claim/pop flows, lock script behavior, sorted-set ordering, pipeline coverage, and TTL mode coverage.

## Recommended Next PER Inputs

- Treat a Redis-compatible endpoint as the first KV-2 candidate, because v0 already consumes Redis/Upstash client libraries and local boot should avoid scattered adapter forks.
- Build a contract test from the TSV rows, not from PgLocalKV's current method list. Include at least `set(... nx/ex/px)`, `expire(... NX)`, `ttl`, `lpush`, `rpop`, `zadd`, `zrange`, `scan`, `pipeline`, `evalsha`, `scriptLoad`, `multi`, and lima-rfc-only `rpush`/`ltrim` as explicit supported-or-unsupported cases.
- Split service semantics from product fixtures: service tests should prove command behavior; v0 integration tests should prove VM pool, web rate-limit readiness, frame token, and credential broker flows against the service profile.
- Decide whether local rate limits remain product-local in v0 or become ordinary Redis-compatible calls. Do not accidentally move rate-limit policy into `local-sandbox`.
- If a Postgres-backed compatibility helper remains a candidate, test concurrent `rpop` claims and lock acquisition under multiple clients before evaluating ergonomics.
